PLANTILLAS REUTILIZABLES HYPER-V / SEMAPHORE

El flujo de uso diario copia una imagen ya instalada. No vuelve a ejecutar
Windows Setup ni Anaconda en cada VM.

DOS PASOS
1. BASE - Windows Server 2025 - instalar una vez:
   playbooks/crear_base_windows_2025.yml
2. BASE - Rocky Linux 9 - instalar una vez:
   playbooks/crear_base_rocky_9.yml
Estas tareas instalan una VM dedicada, verifican el acceso, limpian su identidad,
la apagan y publican una copia de su VHDX como version maestra.

Para crear VM nuevas despues:
- VM desde plantilla - Windows Server 2025: playbooks/crear_windows_2025.yml
- VM desde plantilla - Rocky Linux 9: playbooks/crear_rocky_9.yml
Estas tareas verifican la imagen maestra, hacen copia completa, personalizan el
invitado y registran su nueva identidad de VM en el cluster. Cada disco es
independiente. No necesita la ISO del sistema operativo, ni una clave de indice.

OPCIONES CONFIRMADAS DEL ENTORNO
Hipervisor: SMXHYPVA o SMXHYPVB (Enum).
VLAN de despliegue: 120 o 96 (Enum).
Switch actual de tus encuestas: SETvSwitch.
Catalogo inicial: ws2025-base-v1 y rocky9-base-v1 (Enum segun sistema).
Biblioteca inicial: C:\ClusterStorage\Volume1\VMTemplates.
Si Volume1 no existe/no esta Online, ajustar template_library a un CSV real.
No se crea una carpeta sustituyendo un volumen compartido que no esta disponible.

CREAR LAS BASES UNA SOLA VEZ
Windows: TPL-WS2025, 4 vCPU, 8 GiB RAM, disco de 100 GiB.
Rocky: TPL-ROCKY9, 4 vCPU, 4 GiB RAM, disco de 100 GiB.
IP TEMPORAL para AMBAS instalaciones: 10.138.120.5, VLAN 120, sin DHCP.
Usarlas SECUENCIALMENTE. Un bloqueo compartido de IP impide ejecutar las dos
instalaciones al mismo tiempo. Solo se libera al capturar la base apagada.
Si una tarea falla, conserva el bloqueo: primero revisar/apagar o recuperar la
base. No borrar el bloqueo mientras una VM pueda seguir usando esa IP.
El ping previo detecta algunos conflictos, pero no certifica que la IP este libre.

Faltan completar en la encuesta el gateway y DNS correctos de la red. El prefijo
inicial es 24, tomado de tu encuesta anterior; corregirlo si tu red usa otro.
Las contrasenas se introducen en los campos secretos de Semaphore; no en Git.
Windows utiliza el indice 2 como valor inicial de tu encuesta (Standard Desktop
Experience); se puede elegir otra edicion de la ISO. Confirmar sus indices con
Get-WindowsImage si se cambia el medio. El medio predeterminado es es-ES y su
cuenta Administrador; ajustar windows_ui_language/windows_admin_user si cambia.

Las rutas ISO son las de tus playbooks anteriores. Rocky requiere DVD completo.
La tarea BASE Windows prepara automaticamente una copia UEFI de la ISO con
efisys_noprompt.bin, para arrancar sin pulsar ninguna tecla. Busca el archivo
oficial en la ISO, junto a C:\Oscdimg\oscdimg.exe y en Deployment Tools del ADK.
Si no esta disponible, copiarlo desde el ADK de Microsoft a C:\Oscdimg o definir
efisys_noprompt_path. Tambien admite efisys_noprompt_EX.bin por ruta explicita.
Si falta, la tarea falla antes de crear/iniciar la VM; no deja una instalacion
esperando teclado. La ISO del NAS y su copia original no se sobrescriben.
Secure Boot sigue habilitado. Se estima espacio para tres copias de la ISO
durante la reconstruccion; el arbol extraido se retira al terminar. Se conserva
un registro con el archivo de arranque usado y su SHA256. windows_automatic_boot
esta habilitado por defecto; ponerlo en false vuelve al medio original.
Si Rocky no detecta OEMDRV, agregar al arranque del instalador:
  inst.ks=hd:LABEL=OEMDRV:/ks.cfg inst.repo=cdrom

CONTENIDO MINIMO DE LAS BASES
Windows: sistema operativo, adaptador de Hyper-V, red, WinRM y RDP 4502.
No se une al dominio ni se instalan agentes con identidad propia en la maestra.
Se usa Sysprep /generalize /oobe /shutdown /mode:vm por PowerShell Direct.
No se debe volver a arrancar la VM maestra sellada.
Rocky: @core, SSH, sudo, cloud-init, LVM/XFS y SELinux enforcing. Sin Docker,
nginx ni herramientas de desarrollo. cloud-init se habilita al sellar la base.
Se desactivan los perfiles de red originales, se limpia machine-id, se eliminan
claves SSH de host y se bloquean las contrasenas de las cuentas maestras.
Los clones reciben hashes propios y generan sus claves SSH en el primer inicio.
El usuario operativo usa sudo; root no se habilita para entrar por SSH en el clon.

PUBLICACION
Cada version se guarda como:
  <template_library>\<template_id>\base.vhdx
  <template_library>\<template_id>\metadata.json
metadata.json se publica al terminar la copia, calcula SHA256 y registra el
sistema, version, fuente, tamano y fecha. La imagen queda de solo lectura.
Una version existente nunca se sobrescribe. Para actualizar, anadir otro ID al
catalogo config/plantillas.yml y a las encuestas, y construir una base nueva.
No hay discos maestros reales hasta que termine exitosamente su tarea BASE.
La tarea diaria falla antes de crear una VM si todavia falta esa imagen.

DESPLEGAR DESDE LA PLANTILLA
Seleccionar hipervisor, plantilla y VLAN en listas. Indicar nombre, CPU, RAM,
disco, IP, prefijo, gateway, DNS y credenciales de la nueva VM.
10.138.120.5 queda reservada exclusivamente a la instalacion de las bases.
La tarea no permite usar esa direccion como IP de un clon.
Windows recibe Unattend de specialize/OOBE dentro del VHDX copiado, con nombre,
red y contrasena nuevos. No necesita ISO de instalacion ni de respuesta.
Rocky recibe un medio CIDATA pequeno con metadatos, red por MAC y cloud-config.
Ese medio personaliza el sistema instalado; no instala Rocky otra vez.
Oscdimg sigue siendo necesario en el host para generar el CIDATA de Rocky.
Una MAC nueva fija y un instance-id unico evitan reutilizar la identidad maestra.
Se verifica login real y el marcador de esa instancia antes de retirar los medios
y archivos temporales. La copia del VHDX se verifica contra SHA256 de la maestra.
Si se amplia el disco virtual, la ampliacion de particiones/LVM del invitado
puede requerir un paso adicional; no se afirma que todo ese espacio este ya en / o C:.

REQUISITOS DEL RUNNER Y HOSTS
- Inventario Hipervisores Windows, cuenta con permisos Hyper-V/Failover Cluster,
  montaje de VHDX y administracion del host. CredSSP ya habilitado previamente.
  No se cambian politicas de WinRM/CredSSP ni certificados automaticamente.
- Ansible y Python del MISMO entorno del runner, requisitos de
  requirements-runner.txt, OpenSSH y sshpass para el acceso inicial a Rocky.
- collections/requirements.yml en la raiz de la rama permite instalar
  ansible.windows desde Galaxy. Galaxy no instala paquetes Python ni sshpass.
- El runner debe alcanzar WinRM de los nodos y del invitado Windows (5985), o
  SSH de Rocky (22). NTLM lleva cifrado de mensajes; Basic no se habilita.
- Ambos nodos Up, switch presente en ambos, CSV disponibles y espacio suficiente.
- La instalacion inicial copia la ISO del NAS al CSV; usa credenciales NAS
  opcionales por sesion, sin mappings SMB globales persistentes.
- Las tareas BASE toman iso_path, iso_user e iso_password directamente del grupo
  existente de su sistema (Variables-VM - Windows / Variables VM - Linux).
  No tienen campos de encuesta duplicados para la ISO o credenciales NAS.
  iso_user/iso_password se adaptan a nas_user/nas_pass al invocar PowerShell,
  con password protegido mediante sensitive_parameters. Las tareas de clones
  conservan Empty porque no acceden al NAS ni necesitan la ISO del instalador.
- Los secretos de encuesta pueden ser admin_password, root_password,
  linux_password y nas_pass. Tambien se admiten secretos de entorno HV_*.
- Copias completas en CSV; se necesita espacio para el disco solicitado y reserva.

ERRORES Y PROTECCIONES
No se apagan, sobrescriben ni actualizan VM existentes. Un nombre repetido falla.
diagnosticar_base.yml revisa sin crear VM los nodos, switches, CSV, ISO y bloqueo
de la IP. El paso de preparacion muestra errores y fases; solo se oculta el
valor de la contrasena, en lugar de censurar todo el resultado con no_log.
recuperar_bloqueo_base.yml archiva una reserva fallida conservando owner.json
y registro de recuperacion. Exige failed_task_id y expected_lock_created exacto;
rechaza la recuperacion si existen VM, rol, carpetas o respuesta de la IP.
Excepcion explicita failed_preparation_root: permite archivar tambien una unica
carpeta CSV antes de generar respuestas o discos. Solo admite Media y el arbol
Provisioning/windows-media, sin enlaces, ISO montada ni Oscdimg activo. Conserva
los archivos en SemaphoreVMs/.failed y registra el destino junto al bloqueo.
Oscdimg se ejecuta con stdout/stderr separados y ExitCode comprobado: los
mensajes normales de progreso en stderr no interrumpen WinRM. Sus logs quedan
en Media/oscdimg-uefi.*.log y Media/oscdimg-answers.*.log.
No se hace rollback que borre discos ante errores. Se conservan recursos para
revisar y recuperar; los medios pueden contener contrasenas/hashes.
La captura solo admite una base dedicada TPL- recien creada por este proceso,
con un solo VHDX independiente y sin checkpoints, apagada tras el sellado.
La personalizacion ocurre antes del primer arranque del clon. Una vista previa
RenderOnly no deja el marcador que habilita arrancar la VM.
Las rutas de limpieza se comprueban bajo el CSV y el manifiesto de esa VM.

VALIDACIONES
PowerShell: tests/Verificar-Generacion.ps1 prueba generacion con datos ficticios,
base minima, XML de clone sin windowsPE y semilla cloud-init de identidad unica.
Python: tests/validar_archivos.py verifica YAML, Jinja, referencias y ambos KS.
GitHub Actions comprueba los cuatro playbooks con Ansible --syntax-check y el
sellador Bash. No equivale a haber instalado, sellado y arrancado VM reales.
tests/Verificar-ISOAutomatico.ps1 comprueba argumentos UEFI, rutas con espacios,
preservacion de la fuente, montajes y errores usando dobles de prueba.
Los playbooks originales Windows/ y Linux/ y las tareas 11 y 13 se conservan.
